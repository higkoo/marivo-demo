## 一、这个项目是什么？

一句话：**这是一个"开箱即用"的数据分析项目，用一份名为 Marivo 的工具，分析
纽约市（NYC）官方发布的 2025 全年黄色出租车行程数据。**

把这三件事拆开讲：

### 1. 数据从哪来？
纽约市出租车与礼车委员会（TLC，Taxi and Limousine Commission）每个月都会公开
黄色出租车的行程记录，包含上车/下车时间、地点、里程、车费、小费、支付方式等。
本项目把 2025 年 1 月到 12 月共 12 个月的官方数据全部下载下来，组成一整年的
完整数据集（约 0.7–1 GB，几千万条行程）。

### 2. Marivo 是什么？
Marivo 是一个"语义层（semantic layer）"分析工具。通俗讲：

- 普通方式分析数据，要自己写 SQL，容易写错、口径不一致、换个问题又要重写一遍。
- Marivo 的做法是：先把"数据里有哪些指标、怎么算、有什么注意事项"用代码
  **预先定义好**，存放在 `models/` 目录里。这些定义就像一本"数据字典 +
  计算规则手册"。
- 之后无论你问什么问题，工具都按这本手册来算，保证口径统一、可追溯、不出错。

> 类比：Marivo 像是一位"懂业务规则的分析师助理"，它已经把数据怎么算、
> 哪些记录有问题都记牢了，你只管提问，它按规则给你答案。

### 3. "语义层"是什么意思？
语义层就是把原始数据表里的字段，翻译成"有业务含义、有计算口径"的对象。例如：

- 原始字段 `fare_amount` 只是表里一列数字；
- 在语义层里它被定义为 `fare_revenue`（计价器车费收入），并写明"单位是美元、
  可累加、注意可能包含修正类负值"。

这样一来，提问时不用关心底层 SQL，直接说"我要看车费收入"即可，工具会自动
找到正确的字段和算法。本项目里这些定义都在
[models/semantic/mobility/trips.py](models/semantic/mobility/trips.py)。

### 4. DuckDB 是什么？
DuckDB 是一个轻量级的本地分析数据库。本项目用它把下载的 Parquet 数据文件
整理成一个本地仓库 `data/warehouse.duckdb`。你不需要安装复杂的数据库服务，
它就是一个文件，查询速度很快。

> Parquet 是一种高效的数据存储格式，TLC 官方就用它发布数据。

## 三、开始之前要准备什么（环境要求）

请确认你的电脑满足下面条件，缺一不可：

1. **操作系统**：macOS、Linux 或 Windows 的 WSL（Windows 子系统 Linux）。
   > Windows 用户请先装好 WSL 并能在里面运行命令。
2. **make 工具**：终端输入 `make --version` 能看到版本号即可。
   - macOS / Linux 一般自带；WSL 通常也有。
3. **网络**：初始化时要下载约 0.7–1 GB 的官方数据，请保证网络通畅。
4. **Python**：本机有 Python 3.12 最好；没有也没关系，Marivo 安装器会用 `uv`
   自动准备环境。

> 小提示：如果 `make` 命令不存在，macOS 可装 Xcode 命令行工具
> (`xcode-select --install`)，Linux/WSL 可用包管理器装 `build-essential`。

## 四、手把手开始（5 步走）

### 第 1 步：下载项目代码

```bash
git clone <仓库地址>
cd marivo-yellow-taxi-demo
```

进入项目目录后，你会看到这些重要文件夹：

- `models/` —— 语义层定义（"数据字典 + 计算规则手册"）
- `questions/zh-CN/` —— 6 个中文示例问题，建议从这里开始
- `yellow_taxi_demo/` —— 数据下载、构建、校验的脚本
- `Makefile` —— 把常用命令打包好的"快捷方式"
- `README.md` —— 就是你正在读的这篇

### 第 2 步：一键初始化

在项目根目录执行：

```bash
make setup
```

这一条命令会自动完成全部准备工作。它会依次做这些事，耐心等它跑完
（首次约需几分钟到十几分钟，主要看网速）：

1. **安装 Marivo** 并初始化它的 agent 能力；
2. **下载 12 个月**官方 Parquet 文件（1 月—12 月），支持失败重试和断点续传；
3. **下载**官方 Taxi Zone 区域对照表；
4. **构建**本地数据库 `data/warehouse.duckdb`；
5. **校验数据源**并预览每一个语义对象；
6. **确认**语义目录完全就绪、无警告；
7. **跑一遍真实分析**，覆盖起讫、质量、乘客、费用、时间、速度、小费等路径。

> 这个命令是"幂等"的——重复执行不会出错，已下载完的文件会自动复用，
> 只在需要时才重新构建。所以万一中途断了，再跑一次 `make setup` 即可。

### 第 3 步：确认是否成功

如果最后看到类似 `Yellow Taxi demo setup completed.` 的提示，就说明成功了。
你也可以主动验证一下：

```bash
make data-verify
```

它会检查：月份是否齐全、行程数是否大于 0、区域表是否完整、有没有缺失时间。
看到"verified N months, … trips, … pickup zones"就代表数据没问题。

### 第 4 步：提出你的第一个问题

完成 setup 后，用任意 AI 编程助手（coding agent）打开本仓库，直接用中文提问。
比如可以直接复制下面这段：

> 比较 2025 年 12 月与 1 月的计价器车费收入。收入变化了多少？哪些上车行政区、
> 上车区域、支付方式和费率类别对差异贡献最大？在得出结论前检查数据完整性和
> 异常记录，区分计价器车费与乘客支付总额，并且不要作因果推断。

下面是 6 个循序渐进的示例问题，建议按 01→06 顺序做（详情点击展开）：

1. [车费收入为什么发生了变化？](questions/zh-CN/01_revenue_change.md)
2. [记录的小费率在哪里发生了变化？](questions/zh-CN/02_tip_behavior.md)
3. [哪些需求异常值得进一步调查？](questions/zh-CN/03_demand_anomalies.md)
4. [预测近期 Yellow Taxi 需求](questions/zh-CN/04_forecast.md)
5. [哪些起讫路线最为重要？](questions/zh-CN/05_od_routes.md)
6. [乘客支付金额的构成发生了什么变化？](questions/zh-CN/06_fare_components.md)

每个问题都配有背景小知识和小白提示，建议逐个完成。英文版见 [`questions/en/`](questions/en/)。

### 第 5 步：看懂结果

Agent 给出的分析结果通常包含：

- **总量/对比数字**：例如车费收入从 X 美元变到 Y 美元；
- **分维度拆解**：按行政区、支付方式等拆开的贡献；
- **数据质量提示**：会提醒你哪些记录可能异常、是否影响结论；
- **口径说明**：会区分"计价器车费"和"乘客支付总额"等容易混淆的概念。

> 关键心态：本项目刻意保留了异常记录和修正类记录，以便做数据质量分析。
> 所以看到"不合理记录"是正常的，工具会帮你标出来，而不是偷偷删掉。

## 五、数据模型速览（小白版）

数据库里核心是一张 `yellow_trips` 表，每一行 = 一条官方发布的行程记录。
表里自带"上车"和"下车"两套区域字段，方便做起讫（OD）组合分析：

```text
yellow_trips（每行一条行程）
  ├── picked_up_at          上车时间（纽约当地时间）
  ├── dropped_off_at        下车时间
  ├── trip_distance         里程（英里）
  ├── fare_amount           计价器车费（美元）
  ├── tip_amount            记录到的小费（基本是信用卡小费）
  ├── total_amount          乘客支付总额（不含现金小费）
  ├── payment_type          支付方式（信用卡/现金/…）
  ├── rate_code             费率类别（标准/JFK机场/…）
  ├── pickup_location_id  → pickup_zones   上车区域
  ├── dropoff_location_id → dropoff_zones  下车区域
  └── pickup_* + dropoff_* 角色字段，用于起讫组合分析
```

语义层里"治理好"的核心指标包括：

- **需求量**（行程数）；
- **完整费用组成**（车费、附加费、MTA 税、改善附加费、拥堵费、机场费、CBD 费、小费、过路费）；
- **小费相关**（总记录小费率、信用卡专用小费率）；
- **效率指标**（平均里程、时长、合理速度、每英里票价）；
- **乘客指标**（已知记录的平均乘客数及其覆盖率）；
- **数据质量**（异常记录计数与比率，透明可见）。

维度方面有：上车小时、星期几、是否周末、Taxi Zone、行政区（borough）、
服务区（service zone），可以做运营模式和时间规律分析。

> 关于"合理记录（plausible record）"子集：常用平均值和效率指标不会用全部
> 记录来算，而是只用一组"看起来合理"的记录，规则是公开透明的：
> 上车月份与源文件月份一致、时长 >0 且 ≤24 小时、里程 0–200 英里、推算速度
> ≤100 mph、车费和总额非负、上下车区域都能解析到官方区域。这样算出的均值
> 才不会被离谱记录带偏。而"已发布总量"仍保留全部记录（含异常），方便审计。

## 六、常用命令一览

| 命令 | 作用 | 什么时候用 |
|---|---|---|
| `make setup` | 一键完成安装+下载+构建+校验 | 第一次用，或想完整重置 |
| `make data-verify` | 校验数据完整性与仓库契约 | 想确认数据没问题 |
| `make semantic-snapshot` | 生成语义层快照预览 | 想看语义对象长什么样 |
| `make semantic-check` | 检查语义层是否健康（含 doctor） | 想确认语义定义无误 |
| `make analysis-smoke` | 跑一遍真实分析冒烟测试 | 想确认分析路径都通 |
| `make verify` | 一次性跑完上述所有校验+测试 | 提交改动前的全面体检 |

> 仅供开发/CI 用：可选有界月份子集而不改仓库一年约定：
> `TAXI_DEMO_MONTHS=2025-11,2025-12 make setup`。普通使用者请用完整 setup。

## 七、常见问题 FAQ

**Q：`make setup` 中断了怎么办？**
A：直接再跑一次 `make setup`。已完整下载的文件会复用，不会重头开始。

**Q：下载很慢或失败？**
A：数据源在国外，可避开网络高峰、检查代理；命令本身带 5 次重试和断点续传。

**Q：提示找不到 `make`？**
A：参考第三节"环境要求"安装对应工具包。

**Q：要不要自己写 SQL？**
A：正常分析不用。语义层已经把指标定义好，直接提问即可。原始 SQL 仅作为
"诊断逃生舱"，用完要把结果和语义指标对齐。详见 `AGENTS.md`。

**Q：为什么数据里有负数、零里程这些奇怪记录？**
A：这是官方发布的真实情况（含修正类记录），本项目刻意保留它们，让数据质量
分析能发现问题，而不是悄悄过滤掉。

**Q：小费数据准吗？**
A：基本只记录了信用卡小费（自动记录），现金小费通常不被记录。所以分析
"打赏行为"要专门看信用卡行程，别把现金记录里的零值当成"没给小费"。

## 八、数据来源与注意事项

- 行程记录和数据字典：
  <https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page>
- 官方发布文件：
  <https://d37ci6vzurychx.cloudfront.net/trip-data/>
- Taxi Zone 区域对照表：
  <https://d37ci6vzurychx.cloudfront.net/misc/taxi_zone_lookup.csv>

TLC 说明这些记录由授权技术服务商提供，不保证数据的准确性或完整性。本项目
有意保留不合理记录和修正类记录，以便 Marivo 的数据质量分析能够发现这些问题。
支付类型代码 `5` 和 `6` 的标签遵循 TLC 数据字典。

> 重要原则：本项目把"政策、天气"等解释仅当作**观察性**说明。Marivo 不会
> 从"前后对比"或"相关性"中得出**因果**结论。看到"某政策后收入变化"，
> 描述为"观察到变化"即可，不要说"政策导致了变化"。
